# Research — 竞品调研

主动搜索竞品、用浏览器实际走查产品、截图留证、输出结构化分析报告。**不依赖用户喂资料——自己搜、自己看、自己写。**

<critical-rules>
- 每次调研必须浏览器走查并截图，无截图不算完成
- 事实和建议严格分区——事实有据，建议可推演但不能捏造数据
- 说人话，写给 PM 和下游 Agent 看，不堆术语
- 落盘到工作区，不以聊天代替交付
</critical-rules>

**产出**：
- 被 /propose 触发时：写入 trace 目录（`{trace_path}/research.md` + `{trace_path}/competitive-screenshots/`）
- 独立使用时：写入 `{docs_root}/traces/research/{主题}-竞品分析.md` + `{docs_root}/traces/research/competitive-screenshots/{主题}/`

> `{trace_path}` 由调度方（`/propose`）传入，值为 `{docs_root}/traces/{2hex}/{FEAT-ID}/`（hash-bucket 布局）。独立模式下不使用此变量。

### 模式检查

> 命令中 `<RAY_ROOT>` = 提示头部 `Base directory for this skill:` 路径剥掉末尾 `/skills/<name>`（例 `/.../ray/3.1.0/skills/research` → `/.../ray/3.1.0`）；勿原样传 shell。

```bash
python3 <RAY_ROOT>/scripts/ray/ --resolve-docs-root --json
```

所有模式均允许——竞品调研不依赖代码仓上下文。输出 `{"docs_root": "...", "mode": "..."}` / `{"error": "..."}` / `{"need_user_decision": true, "context": "...", "options": [...]}`。若返回 `need_user_decision: true`，向用户呈现 context + options，等待选择后据此操作（详见 `_trace-persist/references/public-protocols.md`）。

## 流程

### 第 1 步：确认调研范围

和用户确认三件事：

1. **竞品**：3-5 个（用户指定或你根据关键词搜索推荐）
2. **侧重**：产品能力 / 业务规则 / 混合
3. **深度**：按下表自判或用户指定

| 深度 | 触发条件 | 产出 |
|------|---------|------|
| **完整** | 0→1 新产品、新能力、大方向决策 | 七章全写 |
| **标准** | 1→100 迭代、能力增减、交互调整 | 一三四五七（聚焦变更维度） |
| **精简** | 文案优化、配置调整、小范围边界 | 竞品速览 + 功能对比 + 建议 |

**原则**：不确定选更高一档。

### 第 2 步：主动搜索

**不等用户给资料**，用搜索工具主动抓信息：

1. 用户指定了竞品 → 搜官网、产品页、帮助中心、开发者文档、近期公告
2. 未指定 → 按关键词搜同类产品 → 筛 3-5 个 → 逐个核实
3. 优先官方来源；第三方/社区信息标注来源；注明截至日期

**检索维度**（按需选取）：

| 维度 | 要搜什么 |
|------|---------|
| 产品形态 | 入口在哪、独立页还是嵌入式、与核心流程怎么耦合 |
| 能力范围 | 能做什么、不能做什么、是否可操作（下单/仅建议） |
| 用户体验 | 首次使用、空态、出错时怎么处理 |
| 数据与刷新 | 数据来源、更新频率、覆盖范围 |
| 商业模式 | 免费/付费、与会员体系的关系 |
| 多端与国际化 | Web/App/H5、多语言、地区限制 |
| SEO 与内容 | URL 结构、页面层级、结构化数据、内容更新频率 |
| 安全与合规 | 免责声明、风险提示、地区屏蔽策略 |
| 最新动态 | 近期更新、路线图、公告 |

**AI 产品/能力相关时追加**：

| 维度 | 要搜什么 |
|------|---------|
| 自然语言与多轮 | 上下文能力、工具调用、插件 |
| 开发者生态 | API/SDK、Skills 市场、计费 |
| 安全与审核 | 上架审核、举报机制、安全事件 |
| 情境感知 | 行情/持仓/页面上下文感知 |

### 第 3 步：浏览器走查与截图（必选）

<HARD-GATE>
无截图不算完成。这是硬性要求，不可跳过。
</HARD-GATE>

用浏览器打开每个竞品的核心页面，**实际操作一遍**，边走查边截图。

#### 走查内容

**流程级走查**（对比同一任务的步骤数、反馈、异常处理）：
- 设定统一视口 → 各竞品同起点 → 逐步操作 → 每个关键步骤截图
- 截图命名：`{品牌}_{流程}_{step序号}.png`

**页面级走查**（全页结构、信息层级、首屏模块）：
- 打开目标页 → 滚动触发懒加载 → 整页截图
- 截图命名：`{品牌}_{页面简述}_fullpage.png`

#### 截图数量要求

| 深度 | 每个竞品最少截图 |
|------|---------------|
| 完整 | 2 张（主入口 + 第二关键页） |
| 标准 | 1 张（与本次迭代相关页） |
| 精简 | 1 张（最相关的公开页） |

#### 无法访问时

- **反爬/验证码**：记录现象，对可访问的替代 URL 仍须截图
- **仅登录可见**：截公开态 + 标注"登录态待 PM 补图"
- **禁止**用无关页面冒充竞品截图

#### 截图落盘

截图存到 `{docs_root}/traces/research/competitive-screenshots/{主题}/`（被 /propose 触发时存到 `{trace_path}/competitive-screenshots/`）。**写入前 `mkdir -p` 父目录**——`/propose` 不再为 trace 预建目录，research 自己负责创建截图目录。

正文必须包含截图索引表：

```markdown
### 走查说明与截图索引

| 竞品 | 页面 | 视口 | 时间 | 截图 |
|------|------|------|------|------|
| X | 首页 | 1440×900 | 2026-04-26 | ![](competitive-screenshots/{主题}/x_home_fullpage.png) |
```

### 第 4 步：撰写分析报告

按 `references/output-template.md` 对应深度档位写全篇。

#### 事实 vs 建议边界（严格）

| 区域 | 覆盖 | 要求 |
|------|------|------|
| **事实区**（一二三四六章） | 竞品具体怎么做、数据多少、规则是什么 | 有据，不可编造。不可得则写"待核实"或"公开信息未披露" |
| **建议区**（五七章） | 策略建议、优先级、行动项 | 允许推演，但不能捏造竞品数据作为论据。强假设标【推演】【假设】 |

**事实区内的推断**：必须标注"推断"、说明依据，不能把推断写成竞品既定事实。

### 第 5 步：落盘

**被 /propose 触发时**：写入 trace 目录
- 报告：`{trace_path}/research.md`
- 截图：`{trace_path}/competitive-screenshots/`

**独立使用时**：写入 `{docs_root}/traces/research/`
- 报告：`{docs_root}/traces/research/{主题}-竞品分析.md`
- 截图：`{docs_root}/traces/research/competitive-screenshots/{主题}/`

不以聊天代替落盘。

### 第 6 步：协议出口

产物落盘后，调用 `auto_commit_push(TRACE_ID, "research", "竞品调研落盘 — {主题}")`。inline 模式 no-op；external/docs 模式自动 commit + push。

> 协议定义见 `skills/_trace-persist/references/public-protocols.md`。summary ≤ 60 字。

## 规则

1. **不等喂料** — 主动搜索，不依赖用户提供所有信息
2. **必须走查** — 每次调研都要浏览器实打实地看，不能只搜文字
3. **必须截图** — 无截图不算完成，截图落盘到 `{docs_root}/traces/`
4. **事实有据** — 事实区不编造，不可得写"待核实"
5. **建议可推演** — 但不能捏造数据，强假设要标注
6. **说人话** — 写给 PM 和 Agent 看，不堆术语
7. **必须落盘** — 写到文件，不以聊天代替交付
8. **宁深勿浅** — 深度不确定时选更高档位
