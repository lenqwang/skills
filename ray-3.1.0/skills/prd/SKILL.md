# PRD — 逻辑需求文档

从产品简报和竞品调研出发，产出 `/trace` **可以直接消费**的结构化需求文档——开发者拿到 PRD 后不需要再找 PM 澄清，直接出技术方案。

<critical-rules>
- 每个功能/模块必须写到 /trace 不用追问就能出技术方案的粒度
- 数据来源、刷新策略、异常处理必须明确——这些是 /trace 做技术选型的前提
- 不编造接口和技术方案——不确定的标"待研发确认"，但产品侧的决策（数据从哪来、用户看到什么）不能留空
- 说人话，PM 和研发都看得懂
- 边写边审——写完每个章节问自己"trace 拿到这段能直接干活吗？"
</critical-rules>

### 模式检查

> 命令中 `<RAY_ROOT>` = 提示头部 `Base directory for this skill:` 路径剥掉末尾 `/skills/<name>`（例 `/.../ray/3.1.0/skills/prd` → `/.../ray/3.1.0`）；勿原样传 shell。

```bash
python3 <RAY_ROOT>/scripts/ray/ --resolve-docs-root --json
```

所有模式均允许。输出 `{"docs_root": "...", "mode": "..."}` / `{"error": "..."}` / `{"need_user_decision": true, "context": "...", "options": [...]}`。若返回 `need_user_decision: true`，向用户呈现 context + options，等待选择后据此操作（详见 `_trace-persist/references/public-protocols.md`）。

## 流程

### 第 1 步：收集输入

从 FEAT-ID 推算 trace 目录：`{docs_root}/traces/{2hex}/{FEAT-ID}/`

读取目录下的已有文件：
- `trace.md` → 产品简报（/propose 产出）
- `research.md` → 竞品分析（/research 产出，可能没有）

有什么读什么。独立使用（无 FEAT-ID）时，先通过 `/_trace-persist` 创建 trace 得到 ID。

### 第 2 步：判断产品类型和文档深度

| 类型 | 判断依据 | PRD 结构 |
|------|---------|---------|
| **通用产品** | 页面、功能、业务规则类需求 | 标准 7 区块 |
| **AI 产品** | 涉及 Chatbot、Skills、语义交易、AI 能力 | 标准 7 区块 + AI 专项附录 |

| 深度 | 触发条件 |
|------|---------|
| **完整** | 0→1 新产品/新模块、跨多团队协作 |
| **标准** | 功能迭代、能力增减 |
| **轻量** | 小改动、配置调整 |

### 第 3 步：按模块拆解需求

<HARD-GATE>
不能写一大段话描述整个需求。必须按用户可感知的功能模块逐一拆开写。
</HARD-GATE>

**有原型/竞品时**：按页面可见区块拆（/propose 的第 2.5 步应该已经做过）。

**无原型时**：按用户旅程的关键节点拆——进入 → 浏览 → 操作 → 结果 → 异常。

每个模块必须覆盖：

| 要素 | 必须写清楚什么 |
|------|-------------|
| **做什么** | 这个模块的目标，用户完成后达成什么 |
| **入口和前置** | 从哪进来，需要登录/权限/KYC 吗 |
| **主路径** | 触发 → 用户操作 → 系统响应，按步骤编号 |
| **数据** | 展示什么数据、从哪来、多久更新、跨品类是否通用 |
| **交互** | 关键操作——点击、切换、hover 的行为 |
| **状态** | 用户可见的状态名（加载中/空态/出错/成功），何时切换 |
| **异常** | 数据缺失、接口失败、权限不足时用户看到什么 |
| **不做什么** | 这个模块明确排除的能力 |

**写到什么程度算够**：`/trace` 拿到这个 PRD，不用再找 PM 确认任何产品问题，就能直接产出技术方案（组件影响、接口设计、状态机变更）。如果 trace 还得追问"这块数据从哪来"或"出错时用户看到什么"，说明 PRD 没写够。

### 第 4 步：撰写逻辑 PRD

按 `references/output-template.md` 写完整文档。7 个标准区块：

| # | 区块 | 写什么 |
|---|------|--------|
| 1 | 需求背景与目标 | 为什么做、解决什么问题、成功长什么样 |
| 2 | 核心流程 | 全局用户旅程 + 各模块分功能详述（第 3 步的产出放这里） |
| 3 | 数据与依赖 | 数据源、依赖系统、刷新策略 |
| 4 | 边界与限制 | 明确不做什么、已知限制 |
| 5 | 异常场景 | 所有异常的用户可见处理 |
| 6 | 合规与风控 | 地区限制、免责声明、安全要求 |
| 7 | 验收标准 | 可测试的验收条件 |

**AI 产品时追加专项附录**（6 条对齐）：

| 附录 | 内容 |
|------|------|
| 一、输出不确定性 | 分档、重试、降级——用户能感知到的差异 |
| 二、能力与边界合同 | 能做什么、不能做什么、拒答时怎么引导 |
| 三、安全与合规 | 禁止生成的内容类型、数据进模型的范围、AI 标识与免责 |
| 四、评测与观测 | 可观测的行为指标（不是业务 KPI） |
| 五、人机协作与失败路径 | 流式/超时/纠错入口、兜底策略 |
| 六、产品标准集 | Chatbot → 关联 /standards 文档；非 Chatbot → 场景级期望输出表 |

### 第 5 步：边写边审

每写完一个区块，对照检查：

- [ ] 每个功能模块都写了主路径、数据、交互、异常吗？
- [ ] 研发拿到能直接写测试用例吗？还是得追问？
- [ ] 数据源都标了来源吗？没确认的标了"待确认"吗？
- [ ] 验收标准是可测试的吗？（不是"体验好"，而是"点击X后出现Y"）
- [ ] 有没有自己编的数据或接口？
- [ ] 不做的事情写清楚了吗？

### 第 6 步：落盘

写入 `{docs_root}/traces/{2hex}/{FEAT-ID}/prd.md`，打印路径后静默结束。

### 第 7 步：协议出口

调用 `auto_commit_push(TRACE_ID, "prd", "PRD 落盘 — {功能名}")`. inline 模式 no-op；external/docs 模式自动 commit + push.

> 协议定义见 `skills/_trace-persist/references/public-protocols.md`。

## 规则

1. **模块粒度** — 每个功能模块必须写到研发能直接写测试用例的粒度
2. **不编造** — 不确定的数据源、接口、规则标"待确认"，不猜
3. **说人话** — PM 和研发都看得懂，不堆术语
4. **边写边审** — 写完每个区块自检一次，不等写完再审
5. **必须落盘** — 写到文件，不以聊天代替交付
6. **消费者意识** — 表格列名固定，空单元格填"无"或"待确认"，不留空
7. **AI 附录按需** — 只有涉及 AI 能力时才写专项附录，不套模板
8. **竞品不抄** — 引用 /research 结论时用产品语言重述，不粘贴竞品原文
9. **不写代码** — 不写技术实现方案
10. **不写 UI** — 不写页面布局和组件细节
