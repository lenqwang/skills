# 评分维度（100 分）— full 模式

| 维度 | 权重 | 检查项 |
|------|------|--------|
| 需求一致性 | 25 | 每个验收标准都实现了？需求中的每个状态/事件都在代码中？Non-Goals 中的内容没有被实现？ |
| OpenSpec 合规 | 15 | 代码导入并使用 spec 类型？无手工类型重复 spec？无未文档化的额外 API 调用？ |
| 安全性 | 20 | XSS 防护？输入消毒？代码中无密钥？OWASP Top 10 合规？ |
| 代码质量 | 15 | 无硬编码值？无 console.log？无 TODO/FIXME？遵循项目约定（读 CLAUDE.md）？无死代码？ |
| 分级合约合规 | 10 | 按组件模板级别检查（见下方分级检查表） |
| 产品文档就绪度 | 10 | 需求的"产品地图更新要求"章节是否有足够信息供 /update-map 更新组件文件 `modules/{module}/{ComponentName}.md`？新交互/状态机行是否清晰定义？关系变更是否声明？边界情况/故障旅程是否记录？ |
| 治理合规 | 5 | 按需求类型条件检查（见下方治理合规检查表）。如需求无治理合规章节且不涉及触发条件，此项满分 |

## 分级合约合规检查

| 组件级别 | 必检项 |
|---------|--------|
| **轻量** | 无状态副作用、交互行为与 spec 一致 |
| **标准** | + 状态转换与 spec 一致、边界情况已处理 |
| **完整** | + 不变式在所有代码路径上成立、状态机转换完整（无遗漏的合法转换、无未定义的非法转换）、每个故障场景有降级策略和恢复路径 |

## 治理合规检查（条件触发）

| 需求特征 | 检查项 | 不合规后果 |
|---------|--------|-----------|
| 涉及 AI 回复内容 | 安全护栏边界是否在代码中实施？幻觉控制降级策略是否实现？ | 主要问题 |
| FEATURE 级别 | 需求是否定义了成功指标？实现是否支持度量采集？ | 次要问题 |
| 涉及性能敏感路径 | 性能约束是否声明？实现是否符合 trace 治理合规章节中的性能目标？ | 次要问题 |
| 涉及新 UI 组件 | A11y 基线是否满足（键盘导航、屏幕阅读器、对比度）？ | 主要问题 |
| PATCH / REFACTOR | **跳过治理合规检查，此项满分** | — |

## 契约一致性检查

| 检查项 | 方法 | 不合规后果 |
|--------|------|-----------|
| contract_id 存在性 | 遍历所有 `state.json` 中的 `contract_ids`，验证每个 ID 在 `contracts/` 目录下有对应的 YAML 文件 | 阻塞（置信度 10） |
| 生产者/消费者状态兼容 | 对同一 `contract_id`，检查 BE（生产者）与 FE（消费者）的实现状态；消费者不能领先生产者（如 BE 未实现时 FE 不可标记为 done） | 阻塞（置信度 9） |
| OpenAPI 语法校验 | 如 `@redocly/cli` 可用，对 `contracts/` 下所有 YAML 执行 `redocly lint`；工具不存在时输出 warn 并跳过，不阻塞审计 | 工具存在时：阻塞；工具缺失时：信息（warn） |

契约检查在评分中归入 **OpenSpec 合规** 维度（15 分），作为该维度的额外检查项。

## HARD-GATE 阈值

light 与 full 一致：`score >= 80` 通过。HARD-GATE 在两种模式下都生效。

# light ↔ full 映射（仅 full 模式需要）

light 4 维度的来源不是凭空设定，而是从 full 7 维度"吸收 / 重塑"得到。

## 维度权重映射

| light 维度（权重） | full 来源（条目 + 权重） | 关系 |
|-------------------|-------------------------|------|
| 需求一致性 25 | full · 需求一致性 25 | **1:1 直接保留** |
| 安全 20 | full · 安全性 20 | **1:1 直接保留**（仅改名） |
| 测试通过 25 | full · 代码质量 15 + light 新增"测试通过自评" 10 | **N:1 吸收 + 提级**（代码质量的测试相关切片提级为独立维度；新增 10 分自评弥补失去的"代码质量"非测试切片） |
| 不变式保持 30 | full · 治理合规 5 + full · OpenSpec 合规 15 中的不变式相关切片 + light 新增"破坏性自评" 10 | **N:1 吸收 + 重塑**（治理合规在 PATCH/REFACTOR 本就满分放行，权重让渡至本维度；OpenSpec 中"不变式 / 状态机转换"切片归入；新增 10 分自评盯破坏性变更） |

## 1:N 子项映射汇总

| full 子项 | full 所属维度 | light 归宿维度 | 映射关系 |
|-----------|--------------|---------------|----------|
| 验收标准实现 | 需求一致性 | 需求一致性 | 1:1 |
| 状态/事件覆盖 | 需求一致性 | 需求一致性 | 1:1 |
| Non-Goals 反向检查 | 需求一致性 | 需求一致性 | 1:1 |
| spec 类型导入 | OpenSpec 合规 | — | skipped |
| 契约一致性检查 | OpenSpec 合规 | — | skipped |
| **不变式相关切片** | OpenSpec 合规 / 分级合约合规 | **不变式保持** | N:1（吸收） |
| 状态机转换完整性 | OpenSpec 合规 / 分级合约合规 | 不变式保持 | N:1（吸收） |
| XSS / 输入消毒 | 安全性 | 安全 | 1:1 |
| OWASP Top 10 | 安全性 | 安全 | 1:1 |
| 测试通过率 / 覆盖率 | 代码质量 | **测试通过** | N:1（提级 + 加权） |
| 无 console.log / TODO | 代码质量 | 测试通过 | N:1（次要切片归入） |
| 无硬编码 / 项目约定 | 代码质量 | 测试通过 | N:1（次要切片归入） |
| 故障旅程 / 降级策略 | 分级合约合规 | 不变式保持 | 1:1（归入不变式护栏） |
| 产品地图更新清单 | 产品文档就绪度 | — | skipped |
| AI 护栏 | 治理合规 | 不变式保持 | HARD-GATE（独立于评分） |
| 性能 / A11y / 成功指标 | 治理合规 | 不变式保持（自评） | 弱化为自评，不独立扣分 |

> 设计意图：light 用更少维度覆盖 PATCH/REFACTOR 场景的"集中检查"——不变式 + 安全 + 测试 + 需求是 PATCH 必须卡的四道，OpenSpec / 产品文档 / 分级合约的细粒度检查推迟到 FEATURE full 审计或 /digest 周期。
