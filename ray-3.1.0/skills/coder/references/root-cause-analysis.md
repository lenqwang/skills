# 根因分析（10 轮或 5 轮同类后触发）

不只输出 STUCK 报告，走一轮系统化分析：

## Phase 1：症状收集

- 最后 3 轮的错误信息
- 错误模式分布（哪类错误最多）
- 通过/失败测试的分布

## Phase 2：回溯

- 从失败的测试往回追：测试期望什么？spec 定义了什么？代码做了什么？
- 三者之间的矛盾点在哪里？

## Phase 3：假设

根据回溯结果，形成最多 3 个假设：

```
假设 1：spec 与测试存在矛盾（测试期望 X，spec 定义 Y）
假设 2：缺少外部依赖（代码依赖 Z 但 mock 未提供）
假设 3：架构不匹配（当前实现方式无法满足测试期望的接口形状）
```

## Phase 4：输出根因报告

写入 `{docs_root}/traces/{2hex}/{TRACE_ID}/STUCK.md`（per-trace 一次性产物，与 trace.md / audit.md 同目录；目录名已含 ID，文件名无 ID 前缀）：

```markdown
# 根因分析：{TYPE}-{4hex}-{slug}

**状态**：STUCK（{ITERATION} 轮后中止）
**日期**：YYYY-MM-DD

## 症状
- 主要错误类型：{类型}（出现 {N} 次）
- 通过测试：{M}/{Total}
- 最后 3 轮错误摘要：{...}

## 错误模式追踪
| 轮次 | 错误类型 | 修复策略 | 结果 |
|------|---------|---------|------|
| 1 | ... | ... | 失败 |
| 2 | ... | ... | 失败 |

## 假设
1. {假设 1} — 证据：{...}
2. {假设 2} — 证据：{...}
3. {假设 3} — 证据：{...}

## 建议
- 如假设 1 正确：{建议操作}
- 如假设 2 正确：{建议操作}
- 需要用户确认：{具体问题}
```
