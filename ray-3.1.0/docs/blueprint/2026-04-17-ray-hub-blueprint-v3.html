01
拓扑：大脑与四肢
为什么 PD / UI / QA 完全不需要代码仓权限？

产品 acme 有 3 个代码仓：acme-web（前端）、acme-srv-user（用户服务）、acme-srv-pay（支付服务）。所有产品文档、API 契约、需求追踪都集中在第 4 个 git 仓 acme-product-docs——这就是 hub。代码仓只是"接入"hub，并不存储文档。

HUB 内部结构 acme-product-docs/ 里到底有什么
acme-product-docs/ ← HUB · 独立 git 仓 │ ├── product/ ← 产品文档（HUMAN · canonical source of truth） │ ├── PRODUCT-MAP.md ← 产品地图索引（模块总览 + 工作流 + 关系图） │ └── modules/{m}/ ← 按业务模块（auth / billing / ...） │ ├── index.md ← 模块概述（用户旅程 + 组件索引） │ └── {Component}.md ← 组件文件（轻量 / 标准 / 完整 三档模板） │ ├── tech/ ← 技术视角（REFERENCE · 可选 · 有 TECH-MAP.md 才生效） │ ├── TECH-MAP.md ← 系统全景（架构风格 + 依赖 + 部署） │ ├── runtime/ ← 运行时单元（web · h5 · native · services · database · cache · queue） │ ├── concerns/ ← 跨运行时关注点（auth · observability · ci-cd · testing · security） │ └── decisions/ ← ADR（架构决策记录） │ ├── contracts/ ← API 契约（CONTRACT · FE/BE 握手点） │ ├── {module}/ ← 按模块组织（与 product/modules/ 一一对应） │ │ ├── openapi.yaml ← 模块根文件（$ref 引用 paths/ 与 schemas/） │ │ ├── paths/{resource}.yaml ← 按 URL 资源前缀分组（OpenAPI 官方推荐） │ │ └── schemas/{Schema}.yaml ← 模块内 request / response schema │ └── shared/schemas/ ← 跨模块共享类型（Error · Pagination · User） │ └── traces/ ← 需求追踪（SOURCE · file-per-writer 工作区） ├── {TRACE_ID}/ ← active · 一个文件夹 = 一个 trace 完整工作区 │ ├── trace.md ← PD：需求主文件（场景 + 验收 + 规则） │ ├── challenge.md ← Challenge Agent：质疑清单（仅 FEAT/BUG） │ ├── ui.md ← UI：交互流程 + 视觉规范 │ ├── be.md ← BE：API 设计 + 数据模型 │ ├── fe.md ← FE：组件结构 + 状态管理 │ ├── test-plan.md ← QA：测试用例矩阵 │ ├── run.json ← pipeline 执行日志 │ └── state/ ← 各 repo 状态切片（file-per-writer · 零冲突） │ ├── {repo_id}.json ← 每个代码仓写自己的（如 web.json / srv-user.json） │ └── docs.json ← docs 模式下 PD/QA 的操作记录 │ ├── _archive/{TRACE_ID}/ ← digested · 已被 /digest 吸收，仅供追溯 └── *.csv ← gitignored · 派生索引（index/files/apis/tests/tech_debt）
产品文档在哪？
在 hub 仓 acme-product-docs 里。代码仓里没有 docs/product/ 也没有 docs/traces/——全员通过这一个仓协作。
代码仓需要什么？
只需 1 个文件：.ray/config.yaml（入库共享，含 docs_url）。其他人 clone 后第一次跑 ray 命令时，hub 会自动 clone 到 .ray/docs/（gitignored）。零手动配置。
PD 怎么提需求？
直接 cd acme-product-docs 跑 /propose。不需要 clone 任何代码仓。看不到代码也没关系——后续开发会接入。
FE / BE 怎么协作？
通过 hub 里的 contracts/{module}/paths/{resource}.yaml（OpenAPI 契约）握手。BE 写契约，FE 读契约——两人不需要互相读对方代码。
记住这点
权限按角色隔离，但产品文档全员共享。PD/UI/QA 只要 hub 仓权限就能完整工作；FE/BE 各自只看自己代码仓 + hub。没有"我看不到你那边"的理由。

FE接需求
proposed→traced
cd acme-web git checkout -b feat/login-FEAT-a3f7 /trace
  • 从代码分支名自动识别 TRACE_ID = FEAT-a3f7
  • checkout hub 的 ray/feat-a3f7 到 .ray/docs/（自动）
  • 扫描 web 代码做影响分析，向 trace.md 追加 FE 技术方案

3
BE接需求 · 写契约
traced（不变 · BE 加入 repos 列）
cd acme-srv-user git checkout -b feat/auth-api-FEAT-a3f7 /trace
  • 自动 checkout 到 ray/feat-a3f7（PD 在 step 1 已创建，远程已存在则直接复用）
  • 写 be.md（API 设计 + 数据模型）
  • 写契约：contracts/auth/paths/session.yaml（POST /auth/session）
  • index.csv repos 列追加 srv-user · 现在是 [web, srv-user]
4
FE实现
traced→audited
cd acme-web /pipeline
  • 调度 architect → qa → coder → audit → update-map（per-repo 增量）
  • 写 web 的 state/web.json（包含 status、artifacts、contract_ids）
  • FE 实现登录组件 + 调用 BE 契约 contracts/auth/paths/session.yaml
  • 测试通过 + audit 评分通过 → web 视角的 status = audited
5
BE实现
traced→audited
cd acme-srv-user /pipeline
  • 同 4，但写自己的 state/srv-user.json——file-per-writer，永不冲突
  • BE 实现 POST /auth/session + 单元测试
  • srv-user 视角的 status = audited
6
FE+BE各自创建 PR
audited→per-repo shipped
/ship # 在 acme-web /ship # 在 acme-srv-user
  • 各代码仓创建自己的 PR（不是 hub PR）
  • 每次 ship 在 hub 的 index.csv 追加 repo_status：web:shipped, srv-user:shipped
7
FE/BEcode PR 合并
shipped（等待 finalize）
  • web 的代码 PR 合入 main、srv-user 的代码 PR 合入 main——常规 review 流程，ray 不参与
  • 但是！hub 的 ray/feat-a3f7 分支还没有合入 hub main
8
最后合 PR 的人收尾
shipped→digested
/ship --finalize FEAT-a3f7
  • squash-merge hub 的 ray/feat-a3f7 → hub main
  • 跑 /update-map（终态收口模式）：所有 state json 齐全后跨 repo 重算 PRODUCT-MAP
  • 跑 /digest：把 trace 内容归纳进 product/modules/auth/
  • 移动 traces/FEAT-a3f7-login/ → traces/_archive/FEAT-a3f7-login/
  • 删除远程 ray/feat-a3f7 分支 · 任务彻底闭环
多角色协作 DAG (FEAT / BUG) Step 2-5 内部展开 · PATCH / REFACTOR 跳过 Challenge
PD ─► Challenge(PD) ─► PD修复 ─┐ │ ├─► UI ────────────────┐ │ │ └─► BE ─► Chall(BE) ───┤ │ │ └─► contracts/ ◄──┤ │ FE ─► Chall(FE) ◄─┘ │ └─► QC
Challenge Agent 在 PD/BE/FE 产出后自动介入做"魔鬼代言人"质疑（最多 3 轮自愈循环）。FE 等 UI + BE 都通过才动工，QC 等所有产出齐全才动工。pipeline 按 trace.md 头部 roles 字段裁剪 DAG。
记住这点
/propose 是唯一的分支创建者。后续 /trace · /pipeline · /audit · /ship 全部自动 checkout 同一条 ray/{trace_id} 分支，多代码仓写入也只走这一条——这就是"一个 trace = 一条分支"。
03
谁在哪里做什么
5 个角色 · 各自的工作目录 · file-per-writer 怎么消灭冲突
角色 工作目录 主用 skill 在 FEAT-a3f7-login 中产出
PD acme-product-docs/ /propose · /digest · /explore trace.md
UI acme-product-docs/ /propose · /explore ui.md（交互流程 · 视觉规范）
BE acme-srv-user/ + .ray/docs/ 自动同步 /trace · /pipeline · /audit · /ship be.md + contracts/auth/paths/session.yaml + state/srv-user.json
FE acme-web/ + .ray/docs/ 自动同步 /trace · /pipeline · /audit · /ship fe.md + state/web.json
QA acme-product-docs/ + 可选只读各代码仓 /qa · /explore · /audit test-plan.md + state/docs.json
file-per-writer · 为什么 git 永远不会冲突
在 trace 文件夹里，每个角色 / 每个代码仓只写自己专属的文件。两个 writer 不会改同一个文件——git merge 没有可冲突的位置。这是工程上的硬保证，不靠"协调"。
traces/FEAT-a3f7-login/ ├── trace.md ← PD 写 ├── ui.md ← UI 写 ├── be.md ← BE 写 ├── fe.md ← FE 写 ├── test-plan.md ← QA 写 └── state/ ├── web.json ← acme-web 写（FE pipeline 触发） ├── srv-user.json ← acme-srv-user 写（BE pipeline 触发） └── docs.json ← PD/QA 写（docs 模式操作）
记住这点
5 个角色 → 5+ 类专属文件 → git 冲突在设计上不可能。即使 FE 和 BE 同时跑 /pipeline，他们写的是不同 json，rebase 必然成功。
